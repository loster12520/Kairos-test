## L1 · 渲染模型的三条路与为什么选第一条

**背景**：P1 的目标句里有"静态产物"，但 HTML 从哪来，上游没定（Q14）。

**三条路**：
- (a) 构建期在 JVM 上跑同一份 Kotlin 页面描述，渲染成静态 HTML；
- (b) 运行时在 JS 里建 DOM；
- (c) 在编译器插件里写一个 IR 解释器，把整棵组件树常量折叠成 HTML。

**判断**：选 (a)。

**依据**：
- 与目标一致：(a) 与 (b) 的差别就是"HTML 是不是直出的"，而"直出"是方向文档验证信号 1 的原话。
- 风险最低：(c) 最彻底，但它要求插件理解整个 Kotlin 子集，等于把"分析面 = 原语集合"这条契约（D20）打破一次；而且 (c) 失败时无法回退。
- 解耦：(a) 消费的只是"类名是常量"这一个事实，因此它可以在折叠机制被证实之后再选型——H17 由此成立。

**代价（必然付）**：一个页面要跑两遍代码（构建期一次、浏览器一次），于是"构建期渲染"与"运行时行为"必须共享同一套页面描述；这要求节点模型是纯数据，不能有平台 API。

**被否决**：只用 (b)。理由：拿不到 HTML 直出，P1 的目标就少了一半；而且 (b) 的产物无法用静态检查证明任何东西。

## L2 · 页面是纯数据

**判断**：节点模型放在 common 源集，只含 `Node` / `TextNode` / `ElementNode` 与构建器；序列化在 JVM，事件在 JS。

**为什么**：三方（页面描述、HTML 序列化、事件接线）只有页面描述是共享的；把 DOM 类型排除在 common 之外，JVM 才不需要一个假 DOM。

**代价**：构建器是手写的（`div { }`、`h1 { }` 各一行），每加一个标签就要加一行。P3 之前够用。

## L3 · 一次切换是多条类的替换

**事实**：本页的主题变体是"背景色 + 前景色"两条声明，因此一个主题 = 两个原子类。

**发现**：第一版按"单个类名"做替换，结果点一次只换掉半个主题——这是实现 bug，但它暴露的是**模型问题**：一个变体天然是类名集合，不是单名。

**判断**：② 档原语必须以"类名组"为最小单位。

**影响**：这条会改变 P2 的原语签名与产物结构（一个状态对应一组类，而不是一个类）。已记入 [执行报告](round-2.report.md) 第 4 节。

## L4 · 手写样式与分层的关系

**判断**：本轮允许手写 `site.css`（无 layer）压过 `@layer kairos`，并把这条当特性写清楚。

**为什么**：布局、栅格、reset 这类东西用户不想交给编译器；而无 layer 胜过分层是 CSS 规范行为，不需要额外机制。

**风险（可能付）**：用户加一行手写样式就能悄悄改掉变体——P2 做级联代数时必须明确 kairos 层的位置，以及是否需要为"必须赢"的变体提供更高优先级通道。

**本轮确定的结论**：Q14 关闭；② 档按类名组设计；手写样式的优先级问题移交 P2。
