## L1 · 这一轮为什么从"折叠"开始

**背景**：[phases.md P1](../phases.md#p1--编译期样式折叠档可行性证伪) 的核心目的是"证明这条链在真实工具链上跑得通"。P1 里可以做的事很多，但只有一件是**其它所有事的前提**：调用点能不能被编译器替换成常量。

**判断**：把 R1 的范围压到最小——一个原语（`css { }`）、一个后端（Kotlin/JS）、一份产物（CSS + 映射）。

**依据**：在写计划之前先做了一次侦察，结果是"插件能同时看到 `css{}` 调用与 lambda 体内的 `declaration(...)` 调用"。如果这条侦察失败，R1 的计划会完全不同（要改成"先运行后抽取"），所以计划是建在事实验证之上的。

**本轮不做**：渲染层、级联、类型化 helper、Gradle 统一插件——它们都不影响"折叠能不能成立"这个判断。

## L2 · 可判定子集与单入口

**判断**：R1 只认一种写法——lambda 体是**直线序列的 `declaration(字符串字面量, 字符串字面量)`**，别的形状一律不折叠。

**为什么**：
- 可判定子集的边界越窄，越容易在一次实现里做对；边界是后面可以扩的。
- 只留一个入口（`declaration`），插件不需要理解"哪种 Kotlin 语法糖变成了哪种 CSS 属性"这类映射表。

**代价（必然付）**：DX 很差，`css { declaration("color", "#111111") }` 写起来啰嗦。这是刻意的：先把机制证明，再谈糖。

**被否决**：本轮就做类型化 helper + 注解映射。理由：helper 的属性名映射来源（注解 / inline body / 硬编码表）本身是个设计问题，不该混进"折叠能否成立"的验证里。

## L3 · 类名算法必须只有一份

**问题**：类名会在两个地方被算出来——编译期（插件折叠）与运行期（降级路径）。

**判断**：两侧必须是**同一份代码**，而不是"两份实现 + 一致性测试"。

**做法**：插件 jar 把运行时库的 JVM 类打进去，直接调用同一个 `classNameFor`。

**代价**：插件 jar 因此不是"纯编译器代码"，它带着运行时的声明模型；将来运行时变大时，插件 jar 也会跟着变大。可接受——编译器插件本来就是开发期工具。

**另一条被否决的路**：把算法抽成独立小模块，两边都依赖它。它解决不了根本问题——插件运行时没有 classpath，任何外部依赖最终都得打包进去，只是把"打包运行时"换成"打包小模块"。

## L4 · 产物落盘时机

**事实**：Kotlin/JS 的一次构建里，IR 扩展可能被调用不止一次（klib 阶段 + 链接阶段）。

**判断**：规则收集与文件落盘分开——IR 扩展只往收集器里塞，落盘放在 `registerDisposable` 的 `dispose()`。

**为什么**：在 IR 扩展里直接写文件，会在多阶段编译里写出中间态；而 `dispose()` 在编译结束时的语义是明确的。

**顺带的好处**：写出失败被 try/catch 包住，产物写不出来不会让用户的构建失败——产物是附加品，不是编译正确性的前提。

## L5 · 降级对照怎么证明

**问题**："降级不骗人"（契约 3）需要证据，但"骗人"是可观察的：同一份声明，折叠与不折叠应该给出同一个类名。

**做法**：demo 的 JVM 目标**故意不挂插件**，于是它天然是运行时降级路径；JS 目标挂插件，是折叠路径。两侧打印同一批类名，逐字符比对。

**结果**：`hero=cde58b731 c644b24a3` 两侧完全相同；JS 侧 `folds=0` 而 JVM 侧登记表非空——差别只在"谁算的"，不在"算出了什么"。

**本轮确定的结论**：R1 的机制成立；渲染层与级联留给后续轮次（见 [round-2](round-2.md)）。
