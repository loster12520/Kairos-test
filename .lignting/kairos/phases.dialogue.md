## L1 · 接续：本层从哪里开始

**问**：用户原话："现在项目中有两个很粗糙的文档，你需要查看一下，然后提炼出一个可行的计划出来，保存到项目中。我们的token很充足，尽你所能去开发"。

**答**：先完整读了 [direction.md](../../direction.md) 与 [direction.dialogue.md](../../direction.dialogue.md)（D1–D23 / Q9 / H11 全部条目），确认这条方向文档的完整度已经足够排阶段：目标与非目标、不可逆契约、待决问题归属都写清了。本层不再重开方向问题，只做"分阶段 + 核心验收标准"。

**这一层要处理的三个真问题**（不是复述上游）：

1. 上游阶段 1 的"端到端最小闭环"里混了**两件不确定性不同的事**：样式能否被编译器折叠、渲染模型长什么样。混在一起验收，失败了分不清是哪边的问题。
2. Q9（级联优先级代数）上游要求"到本层必须定"，但上游给的四个选项（编译期消解 / `@layer` / 运行时合并 / inline-style）里，前两个各自只能覆盖一半场景。
3. 上游没有规定编译器插件怎么接入构建系统，而这直接决定 P1 的工作量与风险。

**本轮做了前置侦察**（因为"计划必须可行"，不能凭空排）：

- 环境：JDK 21、Gradle 9.0.0、Node 24、Kotlin Gradle Plugin 2.2.20 已在本地缓存、外网可达。`[事实·依据]` 本机探测输出。
- 最小 Kotlin/JS 工程可构建（首次 42s）。`[事实·依据]` `gradle :demo:build` → BUILD SUCCESSFUL。
- **K2 编译器插件可挂载并观察到目标调用**：写了一个只做统计的 `IrGenerationExtension`，在一次真实 Kotlin/JS 编译后写出了如下报告——`[事实·依据]` 编译产物 `spike-report.txt`：

  ```
  dev.kairos.runtime.css -> 3
  dev.kairos.runtime.StyleScope.declaration -> 4
  dev.kairos.runtime.KairosRuntimeRegistry.size -> 1
  ```

  这条报告比任何推断都重要：它同时证明了 (a) 插件在 Kotlin/JS 后端会被触发；(b) `css{}` 的调用点可见；(c) **lambda 体内的 `declaration(...)` 调用也可见**——(c) 是折叠能否成立的关键，若看不到 lambda 体，整个方案要改成"先运行再抽取"，那就不再是编译期方案了。

**本轮不做的**：不重开 α/β/γ（[direction.md 第 2 节](../../direction.md#2-关键决策记录) 已收口于"可穷举"）；不改 D1–D23；不排轮次（那是下一层的活）。

## L2 · 两段式级联的条件与代价

**背景**：Q9 要求在本层定"级联优先级代数的选型"（[direction.md 第 5 节](../../direction.md#5-待决问题)）。上游列的四条出路见 [L3 · 详解点 5](direction.dialogue.md#l3--发散相回到意图层平台之争的更正级联建模详解调试可见性以及身份约束) 的例 2。

**判断**：四条出路里没有一条能单独成立，但把它们**按职责切开**后可以拼成一条：

| 段 | 负责的问题 | 用哪条出路 | 为什么是它 |
|---|---|---|---|
| 第一段：**类别之间**的全序 | base / variant / override / 第三方样式，谁压谁 | `@layer` | 它不动特异性，因此不会引发特异性军备竞赛（上游例 5 已论证）；且 layer 顺序是规范行为，不依赖产物顺序 |
| 第二段：**同一类别内**同属性冲突 | `a + b` 里谁赢、`b + a` 里谁赢 | 编译期消解 | 静态可知时把败者从 class 列表里删掉，产物里根本不发生竞争——这是唯一能表达"顺序即意图"的办法（上游例 2 的核心难点） |

**为什么不是纯 `@layer`**：例 2 的两个意图 `a + b` 与 `b + a` 要产出**不同的 class 列表**，而 `@layer` 只能给"两段样式"一个固定顺序，无法区分调用顺序。层解决的是"类别"，不是"组合表达式内部的先后"。

**为什么不是纯编译期消解**：运行时才知道的组合（②档的类名切换）无法在编译期消解；这时必须有一个不依赖产物顺序的稳定顺序兜底——那就是 layer。

**代价（必然付）**：两段式意味着作者要知道"哪些写法属于同一类别"，判断负担从编译器转移到作者手上（与上游代价②同源）。
**风险（可能付）**：类别边界若按"声明来源"划分，跨模块复用样式时来源会变得模糊（P4 的跨模块聚合会放这个问题）。

**本轮确定的结论**：Q9 收窄为两段式，P2 负责把它落成可测用例；两段都失效时才回到 D21（性能与安全 > 样板）。

## L3 · 渲染模型与 P1 的收窄

**背景**：上游阶段 1 的目标句里同时包含"静态产物"与"在真实小页面里跑起来"（[direction.md 第 8 节](../../direction.md#8-阶段初步勾勒)）。"静态产物"在方向文档验证信号 1 里被表述为"运行时切换代码为 0（HTML/CSS 直出）"，但 HTML 怎么直出，上游没有定。

**判断**：把这两件事拆开验收。

- **样式侧**：`css{}` 能否被编译器折叠成常量、CSS 能否在编译期完整写出。这条**只依赖编译器插件**，与渲染模型无关。
- **渲染侧**：HTML 从哪来。候选有三条——(a) 构建期在 JVM 上跑同一份 Kotlin 代码渲染成静态 HTML；(b) 运行时在 JS 里建 DOM；(c) 编译器插件的 IR 解释器常量折叠整棵组件树。

三条里 (c) 最彻底也最脆（相当于在插件里写一个解释器），(b) 最省事但拿不到"HTML 直出"，(a) 是业界已验证的形态（静态站点生成）。本轮**不选型**，理由是：样式侧如果证伪失败，渲染侧选什么都没意义；而样式侧一旦成立，三条渲染路线都能接上（它们消费的只是"类名是常量"这一事实）。

**本轮确定的结论**：
- P1 的**核心验收标准**只对样式侧负责（[phases.md 第 3 节](phases.md#3-分阶段详述)），HTML 直出作为 P1 内的一个实现轮次，不写进核心验收。
- 新开 Q14（渲染模型选型），归属 P1 的渲染轮次。

## L4 · 阶段划分与排序理由

**判断**：沿用上游的四段骨架，但每段的**核心目的**重写——上游只写了阶段名与边界，没有回答"为什么这一段非在现在做"。

| 阶段 | 上游原名 | 本层核心目的（为什么非现在做不可） |
|---|---|---|
| P1 | 端到端最小闭环（含可行性证伪） | 整套方向**一次真实编译器往返都没有过**。不在这里证伪，后面所有阶段的论证都建在推理上 |
| P2 | 穷举变体成体系 | P1 只证明"一个样式块能折叠"，那是任何静态抽取器都能做到的，**不构成身份** |
| P3 | 封装与开发体验 | 上游代价①③说明建模成本落在作者身上；没有零残留封装，作者会绕开约束（风险③） |
| P4 | 边界外延 | 验证信号 5 要求"写出第二个项目且不改框架源码"，第二个项目必然跨模块 |

**排序判据**（按 `/ltc` 的五条）：每阶段结束系统可用（P1 有一个能打开的页面、P2 有多轴变体、P3 有可反查产物、P4 能跨模块）→ 每阶段可独立验证（核心验收标准都是可跑的命令或可观测的产物）→ 依赖链短（严格串行，不设并行）→ 风险前置（P1 就是最大的不确定性）→ 不横切（没有"每个阶段都改同一处"）。

**为什么严格串行而不并行**：P2/P3/P4 的核心验收都建立在 P1 的产物格式上；并行定义会让"产物格式"变成多方协商的产物，而它的确定性本身就是契约 4。

**本轮确定的结论**：四阶段骨架成立，核心目的重写；接入方式的偏离记入 [phases.md 第 5 节](phases.md#5-与上游的偏离)。
