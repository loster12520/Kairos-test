## 3. 与计划的偏离

| # | 计划 | 实际 | 理由 |
|---|---|---|---|
| 1 | 提取只在含 ternary 的块上做特殊处理 | 统一为"每种组合一组声明"，无 choice 的块只是组合数为 1 的特例 | 两套路径会让类名规则分叉 |
| 2 | `styles()` 对无法解析的操作数报错 | 改为**留在原地不折叠**（运行时拼接），只跳过歧义检查 | 组合本来就是拼接；报错会禁止 `styles(a, compute())` 这种合法写法 |
| 3 | demo-web 的 JVM 目标不需要插件 | 给 JVM 目标也挂了插件 | 提取是模块级决策，两路径必须看到同一份全局信息，否则静态 HTML 与 CSS 错位 |
| 4 | 计划未提 | 发现 htmx 的 `hx-push-url` 深链刷新会拿到片段 | 依据 HX-Request 头返回整页，已加进 E8 |

## 4. 影响后续轮次的问题

1. **提取的边界**：只在同一编译单元内做。跨层同值声明不合（层是类身份的一部分），跨模块同值声明不合（需要全程序知识；事后合并会破坏运行时切换的类）。
2. **组合上限 8**：三个独立二元条件就会超限。真要做组合变体，需要"变体合取"的类名代数，而不是枚举。
3. **共享类让元素类数回升**：块类 + N 个共享类。类数量的收益在 CSS 侧，不在 HTML 侧，这是本次取舍的真实代价。
4. **主题走变量通道**：颜色不再是编译期常量，因此"主题相关的样式"不参与穷举优化——这与方向文档的档③一致，但意味着主题切换的收益来自变量继承，不是类名替换。
5. **深链与片段共用路由**：目前靠 HX-Request 头分流，若将来加更多片段需要统一约定。
