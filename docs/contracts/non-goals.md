# Kairos 非目标清单

- 状态：M0 冻结（2026-10-31）
- 相关：[ADR 0001 产品定位](../adr/0001-product-positioning.md)、[public-api.md](public-api.md)、[versioning.md](versioning.md)

这份清单的作用不是“永远不做”，而是给每个新需求一个默认答案：如果它落在这里，就必须先有 ADR 和版本计划，才能进入路线图。它同时覆盖 plan-1.0 的 M0 要求与 `direction.md` 已有的非目标，冲突处以本清单与 [ADR 0001](../adr/0001-product-positioning.md) 为准。

## 1. 不做虚拟 DOM，不做整树 diff / hydration

- **不做**：运行时构建虚拟树、按 diff 打补丁、把 SSR 标记“激活”成客户端组件树。
- **为什么**：Kairos 的差异点是“样式在编译期算完、页面以 HTML/CSS 为主”；引入虚拟 DOM 会把价值重心移到运行时协调器，和“最小 JS”直接冲突。
- **替代路径**：服务端直出 + 局部增强；列表更新在 M3 用 keyed list 解决，不引入整树 diff；需要复杂客户端状态时，用户可自行接其他库，但不在核心路径。
- **边界**：`bindChildren` 当前是全量重建，这是已知实现限制，不是“虚拟 DOM 替代品”；M3 的 keyed list 也不等于通用 diff。

## 2. 不做自有路由

- **不做**：文件路由、嵌套路由、路由参数解析、代码分割、客户端导航缓存。
- **为什么**：Kairos 优先 Ktor/htmx 的 SSR 场景，路由天然属于服务端框架；自建路由会把框架拖进与 Ktor/React Router 的正面竞争。
- **替代路径**：Ktor 路由 + `page()`/`fragment()`；htmx 的 `hx-get`/`hx-push-url` 由应用决定；官方 recipe 给出深链刷新与片段分流写法。
- **现状**：blog 示例用 `HX-Request` 头在应用层分流整页/片段，框架不提供路由抽象。

## 3. 不做完整表单验证引擎

- **不做**：字段级验证规则 DSL、跨字段依赖、异步唯一性校验、错误消息国际化、表单状态机。
- **为什么**：验证逻辑属于业务与领域层，放进核心会绑定数据库/HTTP 细节；HTML 原生约束与 Ktor 已经覆盖大部分场景。
- **替代路径**：HTML5 约束属性 + 服务端 Ktor 校验；框架只提供错误回显、提交中状态、CSRF hook 的 recipe 与少量属性辅助（M3）。
- **边界**：不会为了“表单体验”在核心引入可控组件与双向绑定。

## 4. 不做 UI 组件市场 / 组件库产品

- **不做**：官方 UI 商城、付费主题、组件市场、设计系统托管、组件版本治理平台。
- **为什么**：这是产品与运营问题，不是编译器/样式契约问题；维护组件库会稀释“薄核心、厚适配器”的路线。
- **替代路径**：第三方组件库可发布自己的样式资产（见 [ADR 0004](../adr/0004-gradle-plugin-artifact-variant.md)）；官方最多提供 recipe 与示例级组件，不作为 1.0 交付目标。
- **边界**：第三方库的兼容责任在库作者；核心只保证类名/manifest 契约。

## 5. 不追求 React/Vue 功能对齐

- **不做**：按 React/Vue 的功能清单补课（Hooks 等价物、Suspense、Transition、Portal、Context、SSR 流式渲染等）。
- **为什么**：对齐会失去取舍标准，最终做成“通用框架的半成品”；Kairos 只优化“可穷举状态 + HTML-first”这一块。
- **替代路径**：需要完整 SPA 能力的团队继续用 React/Vue；Kairos 只服务 Kotlin/Ktor SSR 团队（见 [ADR 0001](../adr/0001-product-positioning.md)）。
- **边界**：比较文档只解释差异，不做“比 React 更好”的营销承诺。

## 6. 不做运行时样式系统

- **不做**：运行时计算样式值、按 props 生成 CSS、在浏览器里插入/修改 `<style>` 标签、CSS-in-JS 的运行时求值。
- **为什么**：与“样式在编译期算完”的身份直接冲突，也会让产物确定性与剪枝失效。
- **替代路径**：三档模型（编译期定死 / 运行时切类名 / CSS 变量通道），见 [ADR 0002](../adr/0002-style-condition-model.md)；需要动态值时写 CSS 自定义属性，而不是让框架算样式。
- **边界**：主题切换只改一个类或变量，不触发样式重算。

## 7. 不做全栈框架

- **不做**：数据库、ORM、认证、权限、后台任务、部署平台、云服务集成。
- **为什么**：这些是 Ktor/生态已有答案；把它们放进核心会让框架无法维护，也违背“薄核心”。
- **替代路径**：官方 recipe 展示与 Ktor、Jimmer、SQLite 等的组合；示例应用可以依赖这些库，但框架模块不依赖。
- **边界**：`kairos-ktor` 只是薄适配器（如果落地），不接管应用架构。

## 8. 不把 Markdown / 富文本放进核心

- **不做**：Markdown 成为 `kairos-core` 的一等能力、富文本编辑器、文档渲染服务。
- **现状差异**：当前 `kairos-core` 里确实有 `dev.kairos.markdown`（标题/列表/引用/代码块/行内格式/链接），plan §4 明确要求 Markdown 不放进核心。这是 M0 已记录的**现实与目标冲突**：迁移方向是拆成可选模块或 recipe，在 M2/M5 处理；在迁移完成前，公共 API 清单把它标为 `experimental`，不承诺稳定。
- **替代路径**：可选模块、第三方 Markdown 库、服务端预渲染。

## 9. 不做 HMR 承诺，不做浏览器兼容军备

- **不做**：承诺热模块替换、任意旧浏览器支持、IE、非 evergreen 浏览器、移动原生与桌面壳。
- **为什么**：plan M4 明确“不要承诺无法兑现的 HMR”；支持范围由 [support-matrix.md](support-matrix.md) 冻结，超出范围不保证。
- **替代路径**：Gradle continuous build + 浏览器自动刷新作为开发期基线；具体 HMR 形态在契约允许后再评估。
- **边界**：支持矩阵里的版本才有测试义务；范围外的问题可以修，但不作为发布门禁。

## 10. 不做非 Kotlin 一等绑定

- **不做**：TypeScript/JSX 入口、Java/Kotlin 双 API、Python/Ruby 绑定、跨语言组件协议。
- **为什么**：身份依赖 Kotlin 的枚举封闭性与类型严密；多语言绑定会让“可穷举”保证退化为运行时约定。
- **替代路径**：其他语言通过 HTTP/htmx 消费渲染结果；Kotlin 是唯一宿主。

## 11. 新功能怎么归类

任何新需求先回答四个问题，答案决定它去哪：

| 归类 | 判据 | 例子 |
|---|---|---|
| **核心** | 直接服务“可穷举状态 + 编译期样式 + HTML 直出”，且不引入领域依赖 | 样式条件、变体轴、挂载点契约 |
| **适配器** | 只做框架与外部生态的薄转换，可独立版本化 | Ktor 适配、htmx swap 重绑 |
| **recipe** | 组合已有 API 解决一类场景，不进库 API | 表单错误回显、CSRF、深链刷新 |
| **暂不做** | 本清单中的条目，或无法证明与身份一致 | 路由、验证引擎、组件市场 |

判断顺序：先看是否违反本清单；再看是否属于核心机制；最后才看用户呼声。**用户呼声不能推翻非目标**，只能推动 recipe 或生态方案。

## 12. 这份清单怎么改

- 删除或放宽任一条目，需要新 ADR、版本计划与迁移说明；不能靠一次 PR 悄悄改。
- 收紧条目（例如把某个 recipe 升级为核心）需要证明它服务于身份，并更新 [public-api.md](public-api.md) 与 [support-matrix.md](support-matrix.md)。
- 与 `direction.md` 的旧非目标冲突时，以本清单与 [ADR 0001](../adr/0001-product-positioning.md) 为准；上游修订完成后再回填引用。
